# SPEC-003 — 최초 UX와 반복 사용

Revision 0.1 · Status Review-ready · 승인 없음 · 관련 R06~R10

## Intent / Scope / Non-goals

첫 방문에 아이디어를 구조화하고, 재방문 때 다음 행동으로 복귀하도록 한다. Screen 01~13의 계약과 상태를 정의한다. 고충실도 시안·실제 프런트엔드 구현은 포함하지 않는다.

공통 언어: `부캐(내 프로젝트)`, `본캐(내 학습)`, `Context(아이디어 요약)`, `Evidence(확인한 근거)`를 첫 노출에 병기한다. 고객 확보, 최소 첫 버전, 고객 한 명당 비용처럼 풀어 쓰고 TAM/SAM·CAC는 설명 안에서만 도입한다.

## Screen 04 — AI 아이디어 인터뷰

| 항목 | 정의 |
|---|---|
| 목적 | 고객·상황·문제·대안·가치를 짧게 구조화 |
| 사용자 행동 | 한 답변, 모르겠음, 질문 건너뛰기, 이전 답 수정, 나중에 계속 |
| UI 요소 | 한 질문+‘왜 묻나요’, 제안/직접입력, 4~6개 핵심 질문 안내, 저장 상태 |
| AI 역할 | 직전 답에 맞는 후속 질문과 구조화 초안; 빈 사실 발명 금지 |
| 저장 데이터 | InterviewSession, 답변, 원문 참조, AIDraft와 생성에 사용한 Context revision |
| 변화하는 스탯 | 타이핑만으로 없음; 확정 전 pending |
| 다음 화면 | 05, 종료했다 돌아오면 같은 질문 |
| 필요한 이유 | 대화 자체가 명세 작성이 됨 |

AI 지연 시 수동 질문 템플릿을 제공한다. 오류 후 답변 보존. 사용자 수정 이후 늦게 온 AI 응답은 오래된 revision이면 적용하지 않는다. 주제가 벗어나면 유연하게 요약하고 사업 질문으로 복귀한다.

## Screen 05 — 프로젝트 Context 확인

| 항목 | 정의 |
|---|---|
| 목적 | AI 초안과 사용자 확정 정보 분리 |
| 사용자 행동 | 항목 수정, 모르는 것 유지, 확정 |
| UI 요소 | 문제·고객·상황·해결·가치의 짧은 카드, 가설/근거/모름 라벨, 펼쳐보는 전체 항목, 수정 diff |
| AI 역할 | 답변 근거를 표시하며 초안 제안 |
| 저장 데이터 | BusinessContext revision, Claim, 사용자 확인자·시각, 출처 연결 |
| 변화하는 스탯 | SPEC-002 단계 1 조건 충족한 축만 최초 상승 |
| 다음 화면 | 최초 06, 이후 수정은 11~12 또는 07 |
| 필요한 이유 | 사용자의 소유권·정정 가능성 보장 |

전체 저장 필드: 이름, 문제, 고객, 상황, 해결책, 핵심 가치, 경쟁/대체재, 수익모델, 현재 단계, 주요 가설, 검증 근거 있는 주장, 모르는 것, 가장 중요한 문제. 모르는 필드는 null+이유로 저장한다. 확인을 눌렀다고 사실 검증 상태를 supported로 바꾸지 않는다.

## Screen 09 — 창업 지식 질문

| 항목 | 정의 |
|---|---|
| 목적 | 현재 행동에 필요한 개념 이해 확인 |
| 사용자 행동 | 짧은 설명, 선택과 이유, 피드백, 다른 문제로 재확인 |
| UI 요소 | 내 프로젝트와 관련된 이유, 질문, 선택지, 정오답 설명, 적용 CTA |
| AI 역할 | 검수한 원문에 근거한 상황화·보충 설명, 정답 정책 변경 금지 |
| 저장 데이터 | LearningAttempt, 문항·개념·콘텐츠 revision, answer, score, feedbackViewed, mastery |
| 변화하는 스탯 | 본캐만; 최초 이해 10 XP, 중복 없음 |
| 다음 화면 | 11~12, 10으로 적용; 오답은 피드백과 새 문제 |
| 필요한 이유 | 강의 소비를 실제 행동 준비로 전환 |

AI가 평가 확신을 못하면 ‘검토 필요’로 저장하고 임의 숙달 지급 금지. MVP는 객관식+이유 선택 위주로 사람 검수 채점 기준을 사용한다.

| 항목 | 정의 |
|---|---|
| 목적 | 답변을 Context·근거·결정으로 연결 |
| 사용자 행동 | 생각/실제 관찰/시뮬레이션 구분, 답변·출처·날짜·한계 입력, 변경안 확인 |
| UI 요소 | 질문 한 개, 지금 묻는 이유, 원문 짧은 인용, 근거 입력, 이전/이후 diff |
| AI 역할 | 누락·모순 질문, Claim/Evidence 연결 제안, 최종 판단은 사용자 |
| 저장 데이터 | ProjectAnswer, Evidence, Claim, Decision(optional), Context revision, GrowthEvent |
| 변화하는 스탯 | 적격 산출물일 때 해당 부캐 단계; 별도 적용 평가 통과 시 본캐 |
| 다음 화면 | 변경안 확인 후 11~12, 변화 없으면 저장 피드백 후 13 |
| 필요한 이유 | 설문으로 끝나지 않고 사업 기록이 변함 |

인터뷰 3명 기록은 각각의 조건·날짜를 분리한다. 익명 식별자를 사용하고 연락처·원문 전체를 필수로 요구하지 않는다. 취소하면 초안만 보존한다.

## Screen 11 — 성장 Reward Dialog

| 항목 | 정의 |
|---|---|
| 목적 | 어떤 사업 변화와 학습이 있었는지 즉시 설명 |
| 사용자 행동 | 변화 확인, 근거 펼치기, 다음 행동/닫기 |
| UI 요소 | 바뀐 사실·가설 먼저, 프로젝트 변화와 내 학습 별도 행, event 근거, 짧은 CTA |
| AI 역할 | 확정 이벤트를 쉬운 문장으로 설명만 함 |
| 저장 데이터 | reward_presented, eventId; 보상 계산은 완료된 서버 트랜잭션 |
| 변화하는 스탯 | 새 지급 없음, 확정 결과 표시 |

오답 학습은 ‘복습 완료’로 시각 피드백. 기준 미달일 때 거짓 +1 금지. 반박이면 “기존 가설과 다른 근거를 찾았어요”를 먼저 표시한다. 실패 결과도 기록할 동기를 유지한다.

## 공통 UI·Data·API 계약

- Web: 넓은 화면에서도 핵심 카드 하나를 우선, 상세는 옆 패널. 모바일/Android: 단일 열과 명확한 하단 주요 행동, 소프트 키보드·뒤로가기 대응.
- 저장 중/저장됨/전송 실패를 분리. 서버 성공 전에 보상을 표시하지 않음. 오프라인은 초안 상태를 분명히 표시하고 재연결 시 중복 키로 제출.
- 접근성: 색만으로 상태 구분 금지, 명시적 레이블, 충분한 대비, 키보드 탐색, 텍스트 확대, 모션 감소. 구체 표준 적합성은 구현 후 검사.
- 상세 API와 데이터는 [아키텍처](../architecture/ARCHITECTURE.md), 보상은 [SPEC-002](SPEC-002-growth.md)를 따른다.

## 2026-09-23 학습 중심 개정 — AUTH-004

진입/홈/학습/적용 흐름은 SPEC-005 r0.1이 우선한다. 한 문장 프로젝트 생성 직후 학습 길에 진입하며, 6문답과 전체 Context 작성은 선행 필수가 아니다. 홈은 다음 학습 한 개를 안내한다. 스탯/근거/결정은 프로젝트 상세에서 확인한다. 개념→문제→내 프로젝트 적용→실행→회고를 연결하며 학습 완료와 현장검증을 분리한다. 기존 데이터 및 SPEC-002 성장 원칙은 유지한다.
