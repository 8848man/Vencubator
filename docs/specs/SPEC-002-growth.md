# SPEC-002 — 7개 스탯과 이중 성장

Revision: 0.1 · Status: Review-ready · Owner: 제품 담당 사용자 · Approval: 없음

## Intent / Scope / Non-goals

사용자가 사업에서 확인한 것과 스스로 학습한 것을 구분하면서 성장을 이해하게 한다. 7개 축, 성장 조건, 보상 원장, 부정적 근거 처리를 정의한다. 사업 성공률 예측·창업가 인증·랭킹·실제 PMF 자동 판정은 제외한다.

관련: R04/R05/R07, [조사 근거](../research/STAT-RESEARCH.md), [ADR-002](../adr/ADR-002-authority.md).

## 2. 부캐 단계 규칙 — FR-G01

각 축은 고정된 하나의 정책 revision을 사용하며 해당 축의 위 산출물 조건으로 판정한다.

| 단계 | 공통 필수 조건 | 의미 |
|---|---|---|
| 0 미착수 | 적합한 산출물 없음 | 부족하다는 평가가 아닌 상태 미확인 |
| 1 가설 정리 | 사용자 확인 가설 + 대상 범위 + 확인 방법 | 구조화됨, 검증됨 아님 |
| 2 현장 확인 | 관련 실제 관찰/문서 1개 이상 + 출처/날짜/방법/한계 + 가설 연결 + 사용자 해석 | 현장 근거를 검토함, 대표성 보장 아님 |
| 3 반복 검토 | 독립적인 관찰 또는 자료 최소 2개 + 일치/불일치 비교 + 대안 해석 | 같은 복제 자료/같은 사람 같은 답은 독립 아님 |
| 4 의사결정 반영 | 단계 3 조건 + 사전 판단 기준과 결과 비교 + 사용자 Decision + 후속 행동 | 하나의 탐구 사이클 완결, PMF·성공 인증 아님 |

전략 축의 단계 2는 실행 결과를 검토한 결정, 단계 4는 대안을 포함한 반복 실험의 종합 결정으로 구분한다. 모든 축을 4까지 채울 필요는 없다. 1명·2개의 근거는 **탐구 과정 이정표**일 뿐 충분한 시장 검증 표본이라는 뜻이 아니다.

`highestMilestone`은 유효하게 달성했던 학습/탐구 이력을 보존한다. `currentEvidenceState`는 별도로 `unknown / mixed / supported / refuted / stale` 중 하나다. 지원 여부는 사용자 해석으로 표시하며 AI 인증이라는 뜻이 아니다. 기한 경과는 자동 실패 대신 `stale/재확인 필요`로 표시한다. 기본 90일 재확인 제안은 조정 가능한 초기 정책이며 실제 수명이라고 주장하지 않는다.

가설 대상·해결책·시장 범위가 변경되면 새 Claim을 만들고 기존 근거의 적용 여부를 재검토한다. 최고 단계는 과거 이력으로만 남기며 현재 범위의 상태를 ‘미확인’으로 표시한다. 업적을 보존한다고 새 아이디어까지 검증된 것으로 표시하지 않는다.

## 3. 본캐 규칙 — FR-G02

개념별 상태: 미학습 → 학습 중/복습 중 → 이해 확인 → 적용 확인. 7일 뒤 새 문제로 재확인을 권한다. 재확인 실패는 복습 상태로 전환하되 과거 XP를 벌점처럼 회수하지 않는다. 앱 내 확인 결과이며 실제 전문가 능력 인증이 아니다.

- 정답 선택과 짧은 이유/예시 선택이 모두 기준을 충족하면 최초 개념 이해 XP 10.
- 오답은 0; 설명을 읽으면 ‘복습 완료’ 시각 피드백. 새로운 동형 문항을 통과하면 해당 개념 이해 XP 최대 10까지 지급.
- 다른 상황 또는 자기 프로젝트의 적용 과제에서 평가 기준(대상·방법·판단 이유)을 충족하면 최초 적용 XP 20.
- 이해/적용 각각 `userId + conceptId + awardType`당 생애 1회. 문구 revision 변경이나 프로젝트 변경으로 재지급하지 않는다. 개념 자체 변경 시 명시적 migration 필요.
- 7일 후 재검사는 숙달 신선도만 갱신하며 XP는 추가하지 않는다. 스팸 접속·정답 공개 후 같은 문항 재시도는 숙달 판정에서 제외한다.
- 본캐는 각 축의 3개 MVP 개념 중 이해·적용한 개수를 보여준다. XP는 보조 표현이다. 더 많은 콘텐츠가 추가돼도 기존 XP를 잃지 않고 학습 범위 변경을 안내한다.
- 자기보고 ‘알아요’만으로 숙달을 부여하지 않는다. 짧은 진단 통과 시 설명을 생략하고 최초 개념 이해 보상 규칙을 동일하게 적용한다.

| AI 인터뷰 답변 타이핑 | 없음 | 없음 | 자동 저장 표시 |
| 사용자 가설 확정 + 단계 1 조건 충족 | 해당 축 최초 단계 달성 | 없음 | “누구의 어떤 문제인지 정리했어요” |
| 퀴즈 이해 확인 | 없음 | 개념 이해 +10 최초 | “고객 인터뷰 질문을 구별했어요” |
| 오답 후 설명 읽기 | 없음 | 숙달/XP 없음 | “복습했어요. 새 질문으로 확인해볼까요?” |
| 실제 인터뷰 기록과 해석 | 조건 충족 시 해당 축 단계 | 자동 없음 | “현장 관찰 1건을 연결했어요” |
| 인터뷰법 적용 평가까지 통과 | 위 조건과 별도 판정 | 최초 적용 +20 | 프로젝트 변화와 내 학습을 별도 행으로 표시 |
| AI 페르소나 긍정 피드백 | 단계 2 이상 불가 | 자동 없음 | “연습에서 나온 질문 후보예요” |
| 기존 가설 반박 근거 | 탐구 조건 충족 시 성장, 근거 상태 refuted | 별도 적용 평가 시만 | 반박과 새 결정을 먼저, 성장 이력은 다음 |
| 동일 요청 재시도/복제 입력 | 없음 | 없음 | “이미 저장한 결과예요” |

단일 활동에는 기본 primaryStat 1개. 서로 다른 산출물·수용 조건을 충족한 경우만 secondaryStat 1개 추가 가능하다. 고객 인터뷰 저장과 전략 Decision은 별도 산출물이 있어야 한다. 본캐/부캐를 합산한 총점은 만들지 않는다.

## 5. Data / API / Error cases

GrowthEvent 원장: eventId, actorId, projectId(optional), sourceActionId, primaryStat, affectedSubject, awardType, priorState, nextState, deltaXp, policyVersion, contextRevision, occurredAt, idempotencyKey, reversalOf(optional).

서버는 원본 Answer/Evidence/Decision 저장과 성장 산정을 한 트랜잭션으로 처리한다. UI가 점수를 쓰거나 AI가 임의 delta를 결정하지 않는다. 클라이언트는 commit 응답의 변경 목록을 표시한다. 중복 키는 같은 결과를 돌려준다. 일부 실패 시 저장과 보상의 불일치가 생기지 않게 전체 취소 후 같은 키로 재시도한다.

근거 삭제·허위 판정·잘못된 채점은 기록 수정이 아니라 정정 이벤트로 파생 상태를 재산정한다. 삭제된 개인정보 원문을 불변 원장에 보관하지 않는다. 개념 숙달과 프로젝트 근거의 적격성이 무효이면 관련 상태를 되돌릴 수 있고 사용자에게 이유를 표시한다. 정상적인 가설 반박은 허위 입력 정정과 구별한다.

오프라인에는 초안만 보관한다. 서버 승인 전에 확정 XP 애니메이션을 보여주지 않는다. 동시 Context 변경은 충돌로 돌려보내 사용자 병합을 요구한다.
