# SPEC-015 — 가치 순간 피드백과 의견 보내기

r0.2 · AUTH-024 (r0.1 AUTH-022) · 2026-09-27 · 상태: 구현 승인. DR-FB-01·02·04·05 결정, DR-FB-03 일부(설정값·규칙 교체 대기)

## 1. 목적과 범위

대량의 연구 데이터가 아니라 **실제로 도움이 됐는지, 어떤 부분이 도움이 됐는지, 어떤 부분이 불편했는지**를 앱 흐름 안에서 모은다. 별도 설문 폼으로 보내지 않는다.

참고 패턴(배달의민족 등 커머스 앱): 사용자가 가치를 경험한 직후, 그 경험 하나에 대해 짧게 묻는다. 본 명세는 이 원리만 차용하며 화면·문구를 복제하지 않는다.

포함: (A) 가치 순간 피드백 카드, (B) 언제든 남기는 ‘의견 보내기’, (C) 로컬 스케줄·보관함, (D) 운영 전송(Firestore, ADR-006), (E) 효용 곡선 데이터 계약.
제외: 보상·XP·스탯 변경(SPEC-002 불변), 응답에 따른 기능 개인화, AI 요약, 관리자 대시보드 화면(후속 W), 푸시/이메일 요청, 인센티브.

## 2. 가치 카테고리와 발생 기준

가치 발생 횟수는 기존 도메인 이벤트(`s.events`)에서 읽기 전용으로 센다. 별도 카운터를 저장하지 않는다(SPEC-013 projection 원칙과 동일). 중복 저장(예: 이미 남긴 기록)은 도메인 이벤트가 생기지 않으므로 세지 않는다.

| 카테고리 | 사용자가 느끼는 가치 | 발생 이벤트(모든 프로젝트 합산) | 카드가 뜨는 화면 |
|---|---|---|---|
| `idea` 아이디어 정리 | 막연한 생각이 고객·문제·해결로 정리됨 | `context_confirmed` | 첫 정리 후 ‘born’ 화면 / 갱신 후 학습 로드맵 |
| `learning` 작은 배움 | 개념·문제를 이해하고 내 프로젝트에 적용 | `lesson_completed` | 학습 완료(준비물 저장) 화면 |
| `evidence` 실행 기록 | 실제 행동 결과를 기록하며 생각이 정리됨 | `evidence_recorded` | 보상 다이얼로그를 닫은 뒤 학습 로드맵 |
| `decision` 방향 결정 | 근거를 보고 다음 방향을 직접 정함 | `decision_committed` | 보상 다이얼로그를 닫은 뒤 기록(journal) 화면 |

‘지금 할 일’ 이어하기·실행 과제 준비는 이어서 입력 흐름이 시작되므로 v1 카테고리에서 제외한다(DR-FB-01).

## 3. 질문 스케줄 — 3, 7, 13, 21 …

- 카테고리별 k번째 질문 슬롯의 발생 횟수 **n(k) = k² + k + 1** → 3, 7, 13, 21, 31, 43 … (간격 4, 6, 8, 10 …). 초반은 촘촘하게, 익숙해질수록 드물게 묻는다.
- **기준선(소급 없음)**: 피드백 로컬 상태를 처음 만들 때 카테고리별 현재 발생 횟수를 `baseline`으로 저장한다. n(k) ≤ baseline 인 슬롯은 묻지 않는다. 기능 도입 시 이미 5회였다면 첫 질문은 7번째 발생이다. 로컬 상태가 지워지면 그 시점 횟수가 새 기준선이다.
- **판단 시점**: 해당 카테고리의 가치 순간 화면(§2)에 도착했을 때만 판단한다. 현재 횟수 n에서 baseline < n(k) ≤ n 이고 기록이 없는 슬롯이 대상이다.
  - 대상이 없으면 표시하지 않는다.
  - 대상이 여러 개면 가장 큰 k 하나만 묻고, 나머지는 `missed`로 닫는다. 쌓아서 연속으로 묻지 않는다.
  - 가치 순간 화면이 아닌 곳에서 횟수가 오른 경우(예: 첫 작은 배움 저장이 아이디어 정리를 함께 확정)는 다음 해당 화면 도착 때 같은 규칙으로 판단한다. 기록에는 실제 발생 횟수 n을 남긴다.
- **전역 빈도 제한**: 가치 카드는 **24시간에 1개, 앱 로드 1회당 1개**까지. 제한에 걸리면 기록을 남기지 않고 대상 슬롯을 그대로 둔다(다음 도착 때 다시 판단).
- **닫힘 상태**: `answered`(점수 선택), `skipped`(‘다음에’·닫기), `unanswered`(표시 후 아무 조작 없이 화면을 떠남), `missed`(더 큰 슬롯에 밀림). 닫힌 슬롯은 다시 묻지 않는다.
- 폼·학습·다른 다이얼로그 진행 중에는 표시하지 않는다(SPEC-013 T03 중첩 금지). 보상 다이얼로그가 열려 있으면 닫힌 뒤 페이지 안에 나타난다.

## 4. 가치 카드 UI

- 형태: 도착 화면의 페이지 제목 아래에 들어가는 **비모달 인라인 카드**. 포커스를 빼앗지 않고 스크롤도 막지 않는다. 닫기(×, 44px 이상)와 ‘다음에’ 제공.
- 1단계 질문(필수, 확정 문구):
  - idea “아이디어를 정리하는 과정이 도움이 됐나요?”
  - learning “이번 작은 배움이 내 아이디어에 도움이 됐나요?”
  - evidence “실행 결과를 기록하면서 생각이 정리됐나요?”
  - decision “근거를 보고 방향을 정하는 데 도움이 됐나요?”
  5단계 척도 — 1 전혀 아니에요 · 2 조금 아쉬워요 · 3 보통이에요 · 4 도움이 됐어요 · 5 아주 도움이 됐어요. 숫자와 문구를 함께 표시(색만으로 구분 금지). `fieldset/legend` + radio, 선택지 최소 48px. 카드 머리말은 “잠깐, 한 가지만 물어볼게요”.
- 2단계(선택): 점수 4·5 → “어떤 점이 좋았나요?”, 1~3 → “어떤 점이 아쉬웠나요?” 카테고리별 칩 다중 선택(§8). 칩은 checkbox 의미.
- 3단계(선택): 한 줄 의견 0~300자, 자리표시 “한 줄로 더 알려주셔도 좋아요 (선택)”. 안내(항상 표시): “이름·연락처 같은 개인정보는 적지 말아 주세요. 보내주신 의견은 서비스 개선에만 쓰고 1년 동안 보관해요.” 입력 폰트 16px 이상.
- ‘보내기’ 1개가 주 행동. 점수만 고르고 닫거나 화면을 떠나도 점수 응답은 확정한다(`answered`, 칩/의견 없음).
- 제출 뒤 카드는 “고마워요! 다음 배움을 더 좋게 만드는 데 쓸게요.” 상태 문구(role=status)로 바뀌고 다음 화면 이동 시 사라진다.
- 320/390/768/1280px 가로 넘침 없음, 모션 감소 존중, 보상·XP 문구와 섞지 않는다.

## 5. 의견 보내기 (언제든)

- 진입: 사이드바 하단(데스크톱)·모바일 메뉴와 설정 화면의 ‘의견 보내기’. 떠 있는 버튼(FAB)은 추가하지 않는다.
- 전용 페이지 `feedback` 뷰(폼은 다이얼로그가 아닌 전용 페이지, SPEC-013 T03). 돌아가기는 들어온 화면으로.
- 제목 “의견 보내기”, 설명 “좋았던 점도, 불편했던 점도 편하게 들려주세요.” 항목: 유형(필수) — 도움이 됐어요 / 불편해요 / 제안 / 오류 · 내용(필수, 5~1000자) · ‘지금 보던 화면 정보 함께 보내기’(기본 켬: 화면 이름·카테고리만). §4와 같은 개인정보·보관 안내를 표시한다.
- 제출 시 토스트 “의견을 받았어요.” 후 이전 화면. 전송 대기 중이면 “연결되면 보낼게요.”
- 폼 초안은 이 브라우저에만 임시 보관, 제출·취소 시 삭제.

## 6. 로컬 저장 (ADR-006)

- 키 `vencubator.feedback.v1` (프로젝트 저장소 `vencubator.prototype.v1`와 분리. 프로젝트 데이터·XP·스탯 스키마 불변).
- 내용: `version`, `respondent`(피드백 전용 무작위 ID, 프로젝트·GA ID와 무관), `baseline`{카테고리: 횟수}, `slots`{카테고리: {k: {n, status, at}}}, `lastPromptAt`, `outbox`(최대 50건, 30일 경과 시 폐기, 넘치면 오래된 것부터), 의견 폼 초안.
- 저장 실패(용량·사생활 모드)는 제품 사용을 막지 않는다. 이때 카드는 표시하지 않는다.

## 7. 전송·데이터 계약

- 대상: 기존 Firebase 프로젝트의 Cloud Firestore `feedback` 컬렉션. 문서 생성만 허용하고 읽기·수정·삭제는 클라이언트에서 금지(보안 규칙 파일 `firestore.rules`).
- 전송 조건: SPEC-011과 같은 운영 호스트(https://vencubator.vercel.app)에서만. localhost·preview·`internal=1`·`lab`은 로컬 보관함에만 남긴다. 사용자가 직접 누른 제출이므로 DNT는 전송을 막지 않는다(DR-FB-05).
- 문서 필드(허용 목록 외 금지):
  `schema`=1 · `kind` value|open · `category` idea|learning|evidence|decision|null · `slot` k(정수)|null · `occurrence` n|null · `status` answered|skipped|unanswered|missed|null(open) · `rating` 1~5|null · `helped`[칩 ID] · `friction`[칩 ID] · `openType` helpful|friction|idea|bug|null · `text` value 0~300자, open 5~1000자 · `view` 고정 화면 이름|null · `concept` 7개 영역 ID|null · `respondent` · `appVersion` · `env` production · `clientTime` ISO 문자열. 서버 생성 시각은 Firestore 문서 createTime을 사용.
- 보내지 않는 것: 프로젝트 ID·이름, 아이디어·답안·준비물·기록 원문, GA 클라이언트 ID, URL query/hash.
- `skipped`·`unanswered`·`missed`도 전송한다(묻는 빈도와 무응답률을 해석하기 위해).
- GA4(SPEC-011)에는 퍼널 집계용으로 `feedback_prompt`(category, slot), `feedback_answer`(category, slot, rating), `feedback_skip`(category, slot), `feedback_open`(open_type)만 보낸다. 자유 입력·칩은 GA로 보내지 않는다.
- 실패 시 outbox에 보관하고 다음 앱 로드 때 재시도. 같은 응답의 중복 전송을 막기 위해 문서 ID는 클라이언트 생성 ID(respondent + 카테고리 + 슬롯, 의견은 무작위)를 사용한다.

## 8. 칩 (확정, ID는 전송 값)

| 카테고리 | 좋았던 점 (`helped`) | 아쉬운 점 (`friction`) |
|---|---|---|
| idea | `clear` 생각이 정리됐어요 · `split` 고객과 문제가 구분됐어요 · `start` 무엇부터 할지 보였어요 | `many` 질문이 많았어요 · `mismatch` 요약이 내 생각과 달라요 · `unsure` 무엇을 적을지 몰랐어요 |
| learning | `concept` 개념 설명이 쉬웠어요 · `quiz` 문제와 해설이 좋았어요 · `apply` 내 프로젝트에 바로 적용됐어요 · `short` 짧아서 부담 없었어요 | `long` 조금 길었어요 · `hard` 어려웠어요 · `mismatch` 내 상황과 잘 안 맞았어요 · `next` 다음에 할 일이 흐릿해요 |
| evidence | `organize` 질문 덕분에 생각이 정리됐어요 · `interpret` 결과를 해석하게 됐어요 · `hint` 다음 방향이 보였어요 | `input` 입력할 게 많았어요 · `unsure` 무엇을 적을지 몰랐어요 · `value` 기록이 어디에 쓰일지 모르겠어요 |
| decision | `overview` 근거를 한눈에 봤어요 · `options` 선택지가 분명했어요 · `record` 결정이 기록으로 남았어요 | `options` 선택지가 잘 안 맞았어요 · `evidence` 근거가 부족했어요 · `burden` 결정이 부담됐어요 |

## 9. 효용 곡선 (측정 정의)

- 한 점 = (카테고리, 슬롯 k, 발생 횟수 n, 점수). 카테고리별로 x=n(또는 k), y=점수 평균·중앙값과 응답 수를 그린다.
- **개인 내 변화**: 같은 `respondent`의 연속 슬롯 점수 차이(Δ)를 모아 “쓸수록 더 도움이 되는지/익숙해지며 떨어지는지”를 본다. 슬롯이 늘수록 계속 쓰는 사람만 남는 생존 편향이 있으므로 전체 평균과 개인 내 Δ를 함께 본다.
- 응답률(answered ÷ 표시)과 skipped·missed 비율도 곡선 옆에 둔다. 응답 수 10 미만 구간은 해석하지 않는다.
- 이 곡선은 제품 판단 참고 신호이며 사업 성공률·학습 성취도 점수가 아니다. S1에서는 Firestore 콘솔·내보내기로 확인하고, 조회 도구는 후속 W.

## 10. 승인 기준 (AC)

F01 스케줄: n(k)=k²+k+1 슬롯에서만 표시, 소급 없음, 24시간·로드당 1개, pending/missed/skipped 규칙을 단위 테스트로 검증.
F02 카운트는 도메인 이벤트 projection. 중복 기록·저장 실패는 세지 않는다. 프로젝트 저장소·XP·스탯 불변(저장 전후 비교).
F03 카드: 비모달, 포커스 이동 없음, 다이얼로그 중첩 없음, 폼·학습 중 미표시, 점수→조건부 칩→의견→보내기, 점수만 고르고 떠나도 확정.
F04 의견 보내기: 전용 페이지, 필수 검증, 들어온 화면으로 복귀, 초안 보관·삭제.
F05 접근성: 320/390/768/1280 가로 넘침 없음, 조작 48px/보조 44px, 입력 16px, 척도 숫자+문구, 스크린리더 이름, 모션 감소.
F06 전송: 운영 호스트에서만, 허용 필드만, 원문 프로젝트 데이터 없음, 실패 시 outbox 재시도·중복 없음, 전송 오류가 앱을 막지 않음.
F07 보안 규칙: 생성만 허용, 필드·타입·길이 검증, 읽기/수정/삭제 거부 — 규칙 단위 검사(에뮬레이터 또는 규칙 파서 검사, 가능 범위 기록).
F08 GA: 4개 이벤트·허용 속성만, 자유 입력 미전송. 기존 SPEC-011 회귀.

## 11. 결정 기록 (DR-FB, 2026-09-27 사용자 확인)

- DR-FB-01 **확정**: 카테고리 4종(idea·learning·evidence·decision). ‘이어하기’ 제외.
- DR-FB-02 **작업자 위임**: 앱 컨셉(창업 부캐 코파일럿, 해요체·짧은 문장)에 맞춰 §4·§5·§8 문구 확정.
- DR-FB-03 **일부**: Firestore 활성화 완료(사용자). 웹 앱 설정값은 기존 Analytics 웹 앱의 `firebaseConfig`에서 `projectId`·`apiKey`가 필요(측정 ID만으로는 부족) — 전달 대기. 보안 규칙은 현재 테스트 모드 → W04에서 제공하는 `firestore.rules`(생성 전용)로 교체 필요. 설정값이 없으면 로컬 보관만.
- DR-FB-04 **결정**: App Check 등 별도 스팸 방지 없음(트리거 빈도가 낮음). 보안 규칙의 필드·길이 검증은 유지.
