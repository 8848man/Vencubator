## 1. Vencubator 제품 철학 재정의

Vencubator는 아이디어를 가진 사람이 다음에 무엇을 확인하고 실행해야 할지 찾도록 돕는 창업 부캐 양성 코파일럿이다.
사용자는 자신의 프로젝트를 키우면서 그 순간 필요한 지식을 배운다.
AI의 역할은 질문하고 정리하며 선택지를 설명하는 것이고, 사업의 방향을 결정하는 사람은 사용자다.
대화의 결과는 일회성 답변이 아니라 수정 가능한 사업 가설과 다음 행동으로 남는다.
실제 행동의 결과는 근거로 축적되고, 사용자는 무엇을 새롭게 알게 됐는지 확인한다.
부캐는 특정 사업에 대한 이해와 검증의 진행을, 본캐는 프로젝트를 넘어 유지되는 학습과 적용 경험을 보여준다.
게임화는 반복 행동과 변화를 이해시키는 표현 방식이며 사업 성공 가능성을 숫자로 보증하지 않는다.
좋은 결과뿐 아니라 잘못된 가설을 발견하고 방향을 바꾸는 일도 성장이다.

**제품 약속:** “오늘 할 작은 행동 하나를 찾고, 실행한 결과로 내 아이디어를 한 단계 더 분명하게 만든다.”

초기 대상은 만들 능력이나 의지는 있지만 고객 검증과 사업 판단 경험이 적은 1인 빌더다. 투자유치 준비 도구나 종합 창업 강의 플랫폼으로 시작하지 않는다. 이 대상 정의는 H01에서 검증한다.

## 2. 기존 제품 분석

두 앱을 실제 브라우저에서 열고 공개 진입 및 프로젝트 화면을 확인했다. 관찰 범위와 미검증 부분은 [실제 관찰 기록](../research/PRODUCT-OBSERVATIONS.md)에 남겼다.

| 제품 | 관찰한 경험 | 계승 | 버리거나 바꿀 부분 | Vencubator의 추가 가치 |
|---|---|---|---|---|
| [Hypora](https://hypora-2026.vercel.app/) | 가입 없이 프로젝트 생성, 한 질문씩 구조화, 첫 버전·테스트·리스크·개요 메뉴 | 질문이 명세가 되는 구조, 사용자 판단, 가설과 근거 구분 | 모든 계획을 완료해야 검증으로 이동하는 선형 흐름은 완화. Context와 맞지 않는 오래된 제안 노출 방지 | 상태별 학습·실행 추천과 지속 성장 |
| [Persoracle](https://persoracle-mvp-v1.vercel.app/) | 자유 설명/항목 전환, 고객 페르소나 선택, 반응 탭, 의사결정 메모, 브라우저 저장 안내 | 다중 관점, 미확인 질문, 비교 후 판단 | 합성 점수를 실제 수요로 해석하는 위험, 결과 revision 불일치, 로컬 중심 보관을 개선 | 시뮬레이션에서 실제 고객 행동으로 연결하고 Evidence를 공통 Context에 저장 |

Hypora 랜딩의 ‘AI 없음’ 설명과 앱의 AI 제안 UI는 일치하지 않았다. Persoracle 샘플 상단 점수와 반응/후속 화면의 상태도 달랐다. 이는 관찰 시점의 표시이며 원인을 단정하지 않는다. 새 AI 반응 생성과 두 앱의 전체 완료 플로우를 모두 검증한 것은 아니다.

세 제품은 **Structure → 가설 점검 → Learn → Improve → Implement → Deploy → Learn**으로 연결한다. 여기서 Persoracle의 AI 페르소나 피드백은 ‘검증 질문을 준비하는 시뮬레이션’이다. 실제 고객 검증 완료라는 뜻으로 쓰지 않는다. MVP에서는 개념과 데이터 구조를 계승하고 기존 앱 직접 통합은 미룬다.

별도 ‘투자’ 스탯은 두지 않는다. 투자가 필요 없는 사업에도 투자유치를 강요하지 않기 위해 수익·재무의 조건부 하위 역량으로 둔다. ‘전략·학습’은 다른 활동의 중복 점수원이 되지 않도록 의사결정 기록이 있을 때만 프로젝트 성장 조건을 충족한다.

7개를 매번 모두 보여주지 않는다. 부캐 홈에는 현재 단계와 관련된 3개, 전체 보기에는 7개를 노출한다. 미착수는 ‘0점 부족’ 대신 ‘아직 살펴보지 않았어요’, 시기상 불필요하면 ‘지금은 보류’로 표시한다.

각 스탯의 부캐·본캐 상승 조건, 대표 질문, 행동, 시각화, 다음 행동은 [SPEC-002](../specs/SPEC-002-growth.md)에 정의했다.

## 4. 본캐 / 부캐 성장 구조

| 구분 | 부캐: 프로젝트 성장 | 본캐: 내 학습 성장 |
|---|---|---|
| 대상 | 해당 프로젝트의 가설과 조사·실험 이력 | 사용자의 개념별 이해와 적용 이력 |
| 권위 데이터 | Context revision, 근거, 실험, 결정 | 학습 시도, 재검사, 적용 평가 |
| 상승 | 모호한 생각을 검증 가능한 가설로 정리, 실제 관찰과 연결, 반복 확인 | 개념 확인 문제, 피드백 후 재검사, 새 상황에 적용 |
| 상승하지 않음 | 접속, 단순 타이핑, 퀴즈 정답, AI가 만든 긍정 피드백만 있는 경우 | 답변 복사, 같은 문제 무한 반복, 피드백 열기만 한 경우 |
| 프로젝트 변경 | 새 프로젝트에서 초기화, 기존 근거 자동 복제 금지 | 유지, 이미 아는 기초 설명 건너뛰기 가능 |
| 의미 | 얼마나 체계적으로 알아보고 판단했는가 | 앱에서 학습·적용이 얼마나 확인됐는가 |

두 성장 모두 실제 창업 능력 전체를 객관적으로 측정한 인증 점수는 아니다.

**부캐의 핵심 분리:** ‘성장 이력’과 ‘현재 가설의 근거 상태’는 다르다. 고객 가설을 반박하는 인터뷰가 나와도 관찰·판단 경험은 쌓인다. 동시에 기존 가설은 ‘반박됨’으로 바뀌며 제품 상태는 ‘재검토 필요’로 표시된다. 성장 연출이 이 경고를 가려서는 안 된다.

프로젝트 스탯은 `미착수 → 가설 정리 → 현장 확인 → 반복 검토 → 의사결정 반영`의 단계 배지로 시작한다. 숫자 레벨이 필요하면 ‘탐구 Lv.’라고 명시한다. 총점·사업 성공률·PMF 백분율은 표시하지 않는다. 단계와 현 상태를 함께 본다.

본캐에는 개념별 ‘학습 전 / 복습 중 / 이해 확인 / 적용 확인’을 둔다. 정답 +1, 오답 후 읽기 +0.5를 곧바로 능력치로 쓰지 않는다. 초기 실험에서는 정답 시 학습 XP 10, 오답 후 재검사 통과 시 최대 10 중 남은 XP만 지급한다. 읽기 자체에는 숫자 보상 대신 ‘복습 완료’ 피드백을 준다. 반복 보상 정책은 명세에서 고정하며 이 수치는 가설이다.

**TeamUp 예시:** “대학생들이 팀플 동료를 못 찾는다”를 “첫 전공 수업의 1학년이 역할과 시간이 맞는 팀원을 찾기 어렵다”로 바꾼다 → 고객 가설 정리 배지. 인터뷰법을 배우고 연습 문제를 통과한다 → 본캐 고객 이해 학습 XP. 실제 대상 3명을 만나보니 모집보다 무임승차가 더 큰 문제였다 → 고객 현장 확인 배지 + 기존 문제 가설 반박. 사용자가 ‘모집 기능보다 역할 합의 실험을 하겠다’고 결정한다 → 전략·학습에 새 결정 이력. 퀴즈만 풀어 고객 검증이 완료되는 일은 없다.

## 5. 핵심 사용자 Loop

### 첫 사용: 목표 5~8분, 검증할 UX 가설

로그인 → 빈 목록의 ‘내 아이디어 만들기’ → 한 문장 입력 → 4~6개 핵심 질문 → 요약 수정·확인 → 부캐 생성 → 가장 중요한 미확인 사항 하나 → 첫 행동 선택.

질문은 ‘누구 / 언제 불편 / 지금 대안 / 제안하는 변화’를 우선 묻는다. 수익모델·시장 크기는 처음부터 모두 채우게 하지 않는다. ‘아직 모르겠어요’를 정식 답으로 저장한다. 이름은 가칭으로 시작할 수 있다. Context에는 미확인 필드도 존재하지만 빈 값을 AI가 사실처럼 채우지 않는다.

### 반복 사용: 앱 안 2~5분 + 필요할 때 앱 밖 행동

1. ‘지난번 다음 행동’을 연다. 진행 중인 실험이 있으면 그것부터 복구한다.
2. 행동을 막는 지식이 있으면 60~90초 설명과 한 문제를 제공한다. 이미 아는 내용은 진단 후 건너뛴다.
3. 프로젝트에 한 문장 적용하거나 실제 고객 행동을 계획한다.
4. 고객 대화·사용 테스트·가격 제안 등은 앱 밖에서 수행한다. 2분 만에 사업 검증이 끝난다고 약속하지 않는다.
5. 결과를 날짜·대상 조건·관찰·한계와 함께 기록한다.
6. AI가 Context 수정안을 제안하고 사용자가 확정한다.
7. ‘바뀐 내용’과 본캐/부캐 보상을 보여준다. 근거가 바뀌지 않으면 저장 완료만 보여준다.
8. 계속/수정/보류 중 사용자가 결정하고 다음 행동 하나를 남긴다.

추천은 최저 스탯 자동 선택이 아니다. 현재 결정에 영향을 주는 미확인 가설, 단계 적합성, 실행 가능 시간, 진행 중 행동을 고려한다. 예: 아이디어 단계에는 재무 스탯이 낮아도 고객 문제를 먼저 확인한다. 개인정보 처리 제약처럼 진행을 막는 항목은 먼저 표시한다.

### 알림의 재방문 이유

첫 행동을 선택한 뒤에만 알림 동의를 제안한다. 초기 기본 제안은 사용자가 지정한 주 2회, 하루 최대 1회, 현지 시간 21~09시 조용한 시간이다. 실제 활성화는 사용자 동의 이후다. ‘레벨을 잃어요’ 대신 ‘TeamUp: 약속한 인터뷰 결과를 남기면 다음 실험을 고를 수 있어요’처럼 미완료 과제와 결과를 연결한다. 완료·보류·삭제된 프로젝트는 발송 직전에 제외한다. 거부해도 앱 안 다음 행동은 유지한다.

## 6. MVP 범위

### 12주에 검증할 최소 완결 경험

**한 프로젝트에서 실제 행동 → 근거 → 판단 → 다음 행동을 두 번 반복하고, 학습한 개념을 다른 상황에 적용할 수 있는가?**

| 반드시 포함 | 범위 제한 |
|---|---|
| 로그인·복수 프로젝트·중단 복구 | 개인 계정만, 협업 없음 |
| 짧은 AI 인터뷰·수정·확정 Context | 한 번에 한 질문, 주요 필드 4~6개 우선 |
| 7개 고정 스탯·이중 성장 | 고객/제품/전략을 깊게 검증, 나머지도 최소 콘텐츠 제공 |
| 질문·짧은 학습·적용 | 7영역 각 3개 개념, 개념별 최초/재검사용 최소 2문항: 총 21개 개념·42문항을 사람 검수 |
| 근거·결정·다음 행동 | 링크/요약·익명 관찰 기록. 대용량 파일/녹음 자동분석 제외 |
| 성장 다이얼로그·접근 가능한 애니메이션 | 기본 캐릭터 1종과 단계별 표현, 꾸미기 상점 없음 |
| 알림·딥링크 | Android 동의 기반 알림과 공통 앱 안 알림. Web 푸시는 후순위 |
| Web·Android 공통 데이터 | Web 베타, Android Internal/Closed Testing 및 실기기 핵심 흐름 |
| 계측·오류 추적·핵심 테스트 | 루프 완성과 데이터 무결성 중심 |

**제외:** 복잡한 캐릭터 수집, 랭킹, 길드, 연속 접속 벌점, 결제/구독 구현, 투자자 매칭, AI의 자율 사업 결정, 자동 코딩·배포, 외부 도구 실행, 기존 앱 자동 import, 실시간 협업, 다중 AI 페르소나 엔진, 전면 오프라인 동기화, 방대한 강좌 라이브러리. 시뮬레이션의 입력/출처 구분은 모델에 반영하되 엔진 구현은 이후다.

## 7. 최초 UX

13개는 정보·상호작용 단위이며 매번 13개 페이지를 순서대로 통과하지 않는다. 11~12는 공통 오버레이/컴포넌트다. 첫 진입에 본캐 전체 대시보드를 강제로 보여주지 않는다.

| Screen | 핵심 목적 | 다음 흐름 |
|---|---|---|
| 01 로그인 | 계정으로 성장과 프로젝트 보관 | 02 / 원래 딥링크 |
| 02 프로젝트 목록 | 만들기 또는 이어하기 | 03 / 07 |

| 04 AI 아이디어 인터뷰 | 질문으로 가설 구조화 | 05 |
| 05 Context 확인 | AI 초안 수정·사용자 확정 | 06 / 07 |
| 06 부캐 생성 연출 | 내 프로젝트가 생겼다는 소유감 | 07 |
| 07 부캐 대시보드 | 가장 중요한 행동 하나 | 13 / 09 / 10 / 08 |
| 08 본캐 대시보드 | 무엇을 배우고 적용했는지 | 09 / 07 / 02 |

| 13 다음 행동 | 시간·이유·완료 기준이 있는 과제 선택 | 09 / 10 / 07 |

각 화면의 **목적·사용자 행동·UI 요소·AI 역할·저장 데이터·스탯·다음 화면·필요 이유**는 [13개 화면 명세](../specs/SPEC-003-ux.md)에 모두 정의했다. 로딩·실패·뒤로가기·오프라인·권한·동시 편집도 포함한다.

초기 홈 예시: `TeamUp / 이번에 확인할 것: 팀원 모집이 가장 큰 문제인가요? / [고객 한 명에게 물어보기] / 최근 변화: 고객 상황을 좁혔어요 / 고객: 가설 정리 · 근거 미확인 / 제품: 아직 살펴보지 않음 / 전략: 첫 행동 선택`. 백분율로 사업이 62% 완성됐다고 표시하지 않는다.

## 8. 핵심 검증 가설

아래 수치는 업계 기준이 아닌 **초기 의사결정 기준 제안**이다. 작은 표본에서는 통계적 효과를 확정하지 않고 분자/분모·이탈 이유를 함께 기록한다. 테스트 계정 제외, 첫 활성화 코호트 기준, 사용자의 복수 프로젝트는 사용자당 한 번만 센다.

핵심 지표: **주간 근거 기반 결정 사용자 수**. 한 주에 실제 관찰을 포함한 Evidence를 저장하고, 그 근거를 참조한 Decision과 다음 행동을 확정한 고유 사용자 수다. AI 시뮬레이션·앱 접속·퀴즈만으로는 충족하지 않는다. 보조 지표로 해당 주 eligible 활성 사용자 대비 비율을 함께 본다.

| ID | 가설 / 방법 | 초기 판단 기준 | 실패 시 대응 |
|---|---|---|---|
| H01 | 8~12명 사전 인터뷰에서 ‘무엇을 검증할지 몰라 멈춤’과 기존 대처 확인 | 절반 이상이 최근 4주 구체 경험과 대처 시도를 말함 | 대상·핵심 문제 재선정, 기능 확대 금지 |
| H02 | 신규 15~25명 중 첫 세션에서 Context 확인과 첫 행동 선택 | 60% 이상, 완료자 중앙값 8분 이내 | 질문 축소, 로그인/용어/요약 수정 |
| H03 | 활성화 후 7일 내 실제 행동 근거와 결정 기록 | 활성화한 사용자 중 40% 이상 | 퀴즈 보상 축소, 행동 크기·모집 방법 보완 |
| H04 | 4주 동안 서로 다른 날짜의 실제 행동→결정 루프 2회 | 28일 관찰 가능한 활성화 사용자 중 30% 이상 | 루프 필요성 재검토, 알림 증량으로 덮지 않음 |
| H05 | 8~10명에게 높은 탐구 단계+반박된 가설 사례를 설명하게 함 | 80% 이상이 점수≠성공과 반박 의미를 설명 | 숫자 레벨 숨기고 단계/근거 중심으로 수정 |
| H06 | 학습 직후와 7일 후 새로운 상황 적용 문제, 평가 기준 사전 고정 | 대응 표본의 60% 이상이 핵심 오류 없이 적용 | 재학습 방식 수정, XP와 숙달 분리 강화 |
| H07 | 알림 동의자에게 동의된 범위에서 무작위 알림일/대조일 비교 | 알림 후 48시간 내 의미 행동 증가 방향 + 피로 호소 20% 미만 | 빈도 축소·행동 가치 개선. 표본 작으면 효과 미확정 |
| H08 | 두 번째 가상 프로젝트에서 기존 개념 활용, 8명 질적 과제 | 6명 이상이 기초 설명 없이 적용하면서 새 근거 필요를 인식 | 건너뛰기 UX·전이 과제 수정 |
| H09 | 파일럿 종료 후 전후 Context 비교와 유료 의향 인터뷰 | 구체적인 반복 가치와 대체 지출 확인 | 단순 ‘쓰겠다’ 답은 수요로 간주하지 않음 |

H07의 인과 효과는 시간·학습 경향과 소표본 제약이 있으므로 탐색으로 해석한다. H09는 가격 검증 완료가 아니며 결제는 MVP 범위 밖이다. 사업 성장의 외부 결과는 사용 테스트·재사용·지불 같은 별도 지표로 기록하고 앱 스탯과 분리한다.

## 2026-09-23 학습 중심 개정 — AUTH-004

진입/홈/학습/적용 흐름은 SPEC-005 r0.1이 우선한다. 한 문장 프로젝트 생성 직후 학습 길에 진입하며, 6문답과 전체 Context 작성은 선행 필수가 아니다. 홈은 다음 학습 한 개를 안내한다. 스탯/근거/결정은 프로젝트 상세에서 확인한다. 개념→문제→내 프로젝트 적용→실행→회고를 연결하며 학습 완료와 현장검증을 분리한다. 기존 데이터 및 SPEC-002 성장 원칙은 유지한다.
